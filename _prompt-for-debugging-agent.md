## Deployment Pipeline

```yaml
# .github/workflows/static.yml
name: Deploy to GitHub Pages
on:
  push:
    branches: ["main"]
  workflow_dispatch:

jobs:
  build-and-deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist
      - id: deployment
        uses: actions/deploy-pages@v5
```

Key points:
- Branch: `main`
- Build: `pnpm build` (which runs `vite build`)
- Artifact: `dist/` directory
- No post-build processing
- Custom domain configured via GitHub Pages settings (not via CNAME file in repo)
- Concurrency group: `"pages"`, cancel-in-progress: false

## Social Preview Mechanism

### How it works (code level):

1. **`index.html`** has generic OG tags:
   ```html
   <meta property="og:title" content="Pet projects" />
   <meta property="og:image" content="https://pet-projects.govgolenko.ru/og-image.png" />
   <meta property="og:url" content="https://pet-projects.govgolenko.ru/" />
   ```

2. **`vite.config.ts`** has a custom Vite plugin `ogPagesPlugin()` that runs in `closeBundle()`:
   - Reads `dist/index.html`
   - For each page in `seo-data.ts` (lens, agenda), replaces the `<!-- Social preview -->...<title>` block with page-specific OG tags
   - Writes to `dist/<page-id>/index.html`
   - This produces different HTML files for `/agenda/index.html` and `/lens/index.html`

3. **`seo-data.ts`** defines:
   ```ts
   pages: [
     { id: "lens", title: "Симметричная линза...", ogImage: "lens-preview-light.png" },
     { id: "agenda", title: "Повестки: Запад vs Кремль", ogImage: "agenda-preview-light.png" }
   ]
   ```

4. **`App.tsx`** also dynamically updates OG tags client-side via `updateSeo()` function (for SPA navigation). This only affects browser rendering, not crawler pre-render HTML.

5. **`public/404.html`** is the GitHub Pages SPA fallback:
   ```html
   <script>
     sessionStorage.redirect = location.pathname;
     location.replace("/");
   </script>
   ```
   This stores the path and redirects to `/`, where the App component reads `sessionStorage.redirect` to recover the page.

### What crawlers see (NO JavaScript execution):

When a crawler (facebookexternalhit, Twitterbot, etc.) fetches `/agenda/`:
- GitHub Pages serves `dist/agenda/index.html` directly (it exists as a static file)
- This file contains page-specific OG tags (generated by `ogPagesPlugin`)
- The crawler does NOT execute JavaScript, so the SPA fallback is irrelevant

## iOS Safe-Area Issue

### Current CSS Architecture:

```css
/* theme.css */
html, body {
  width: 100%;
  min-height: 100dvh;
  min-height: 100vh;
  margin: 0;
  background: var(--bg);        /* #07070a dark / #f4f6fa light */
}
html { background: var(--bg); }
body { background: var(--bg); }

#root {
  width: 100%;
  min-height: 100dvh;
  min-height: 100vh;
  margin: 0;
  background: var(--bg);
  overflow-x: hidden;            /* ← IMPORTANT: creates scroll container */
}
```

```tsx
// App.tsx — injected <style>
#root::before {
  content: "";
  position: fixed;
  inset: 0;
  background: var(--bg);
  z-index: -1;
}
```

```tsx
// App.tsx — dynamic JS (useEffect)
rootRef.current.style.overflow = tab !== "home" ? "hidden" : "";
```

```html
<!-- index.html -->
<meta name="viewport"
  content="width=device-width, initial-scale=1.0, viewport-fit=cover, maximum-scale=1.0" />
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />
<meta name="theme-color" content="#07070a" media="(prefers-color-scheme: dark)" />
<meta name="theme-color" content="#f4f6fa" media="(prefers-color-scheme: light)" />
```

### Element layout (DOM tree):

```
<html background="var(--bg)">
  <body background="var(--bg)">
    <div id="root" background="var(--bg)" overflow-x="hidden">
      ::before { position: fixed; inset: 0; background: var(--bg); z-index: -1 }
      <div class="App wrapper" minHeight="100dvh" position="relative" overflowX="hidden">
        [dynamic overflow: hidden on non-home tabs]
        <HomePage OR LensPage OR AgendaPage>
          [page content with safe-area padding]
        </page>
      </div>
    </div>
  </body>
</html>
```

### Safe-area padding usage:

| Element | Top | Right | Bottom | Left |
|---|---|---|---|---|
| `.home-page` | `48px + inset-top` | `20px + inset-right` | `32px + inset-bottom` | `20px + inset-left` |
| `AgendaPage` div | `48px + inset-top` | `20px` (NO inset) | `48px + inset-bottom` | `20px` (NO inset) |
| `LensPage` div | none | none | none | none |
| GlassPanel (desktop) | `16px + inset-top` | — | — | `16px + inset-left` |
| GlassPanel (mobile) | — | — | `16px + inset-bottom` | `12px` (NO inset) |
| App header (back btn) | `16px + inset-top` | — | — | — |

### Key concern — `overflow` + `position: fixed` interaction:

In CSS, when an element has `overflow: hidden` (or `overflow-x: hidden`), it creates a scroll container. On **iOS Safari**, this has been known to interfere with `position: fixed` children:

1. `#root` has `overflow-x: hidden` in CSS
2. The App wrapper gets dynamic `overflow: hidden` on non-home tabs
3. `#root::before` is `position: fixed` — should cover entire viewport including safe areas
4. On iOS Safari, the combination of `overflow` on ancestor + `position: fixed` on child can cause the fixed element to not extend into safe area insets
5. This would leave the safe area background up to the browser default (which may be different from `var(--bg)`)

### What to investigate for iOS safe-area:

1. **Run `pnpm build` and verify dist** — check that `dist/agenda/index.html` and `dist/lens/index.html` exist with correct OG tags
2. **Inspect the full CSS cascade** — look at the compiled `dist/assets/*.css` to confirm all rules
3. **Test the overflow interaction** — the key hypothesis is:
   - `overflow-x: hidden` on `#root` (theme.css:72) creates a scroll container
   - Dynamic `overflow: hidden` on App wrapper (App.tsx:70) makes it worse
   - `#root::before` with `position: fixed` may not extend into safe areas when parent has overflow
4. **Test on actual iOS device** (or simulator) — this is the ONLY way to confirm. Cannot be verified via HTTP/curl.
5. **Consider these alternative hypotheses**:
   - The `theme-color` meta tag might override the viewport background in safe areas
   - `apple-mobile-web-app-status-bar-style: black-translucent` might not work as expected
   - `100dvh` might behave differently in standalone PWA mode on iOS
   - The `color-scheme: dark light` declaration might affect system UI rendering
   - A pseudo-element or browser chrome might be creating the stripes

### Specific files to modify (if root cause is confirmed):

If the overflow hypothesis is correct, the fix involves:

1. **`src/theme.css`** — remove or change `overflow-x: hidden` on `#root`
2. **`src/App.tsx`** — remove the dynamic `overflow` toggle (`rootRef.current.style.overflow = ...`)
3. **`src/App.tsx`** — consider moving `#root::before` background to `<html>` or `<body>` level
4. Possibly **`src/pages/HomePage.tsx`** and subpages — ensure their own overflow handling is self-contained

### Alternative approaches:

- Use `clip-path: inset(0)` instead of `overflow-x: hidden` to prevent horizontal scrolling without creating a scroll container
- Use `contain: paint` on `#root` instead of overflow
- Move the background painting to `html`/`body` level using a `<style>` tag in `index.html`
- Use `background-color` directly on `<body>` (already present) and remove `#root::before` entirely
